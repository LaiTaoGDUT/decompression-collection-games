## 1. 阶段目标

本阶段把现有架构原型推进为包含两款正式游戏、可以交给真实用户完整游玩的版本：

- 大厅具备正式首屏、品牌识别、统一双列游戏卡列表、列表末尾敬请期待卡、历史成绩、设置和必要状态反馈。
- “合成大西瓜”无需首次引导即可直接开始并理解玩法，具备稳定手感、完整难度与计分、暂停、续玩、结算、重开和存档闭环。
- “霓虹 2048”提供完整 4×4 数字合并玩法、触控/键盘输入、暂停、2048 普通里程碑、4096 最终目标庆祝层、无步可走、结算、重开和本地纪录闭环。
- 大厅与每个小游戏分别拥有独立设计的正式 UI、美术、图标、动效和声音方向，仅共享安全区、可用性、状态语义和工程质量基线。
- 接入微信正式广告能力，完成激励视频和受控插屏，并确保广告不可用时仍可正常游玩。
- 完成开发者工具、微信真机和小规模用户试玩，使版本达到“首个可玩版本”质量门槛。

本阶段首发可玩内容包含“合成大胖橘”和“霓虹 2048”，游戏列表末尾展示一张不可交互的“更多游戏，敬请期待”系统占位卡。`blocks3d` 保留为架构与 3D 回归样例，但不继续产品化，也不在首发大厅向普通用户展示。

## 2. 产品基线

- 目标平台：微信小游戏。
- 屏幕方向：单手竖屏，设计基准 750 × 1334，适配安全区与常见长屏。
- 目标体验：规则直观、操作低门槛、单局约 2～8 分钟、失败后可快速重开。
- 核心循环：合成大胖橘采用投放与物理合成；霓虹 2048 采用四向滑动、同值合并、生成新数字、经过 2048 普通里程碑并在 4096 庆祝层选择继续挑战/完成本局/返回大厅，或无步可走后结算。
- 首发目标：不依赖登录、联网存档、排行榜或运营后台，也能完成完整本地游玩闭环。
- 商业化原则：广告不遮挡核心操作、不在首局强制出现、不因加载失败阻断游戏、奖励只在完整观看后发放。
- 大厅陈列原则：游戏列表固定使用双列网格；全部真实游戏卡同尺寸、同信息层级、同交互权重，不设置主推游戏或跨列大卡；末尾敬请期待卡与游戏卡同尺寸但明确不可交互。

## 3. 本阶段不包含

- 第 3 款及后续正式小游戏和 3D 推倒积木的内容扩展。
- 账号、云存档、好友排行、活动、任务、成就和分享裂变。
- 远程运营后台、A/B 实验和正式数据仓库。
- 完整品牌 IP、规模化角色设定和高成本宣传素材。
- 正式提审、灰度与全量发布；本阶段只做到可交给用户试玩的候选版本。

这些内容留给后续独立计划。本阶段需要的大厅、游戏 UI、美术、动效和广告属于首个可玩版本的必要范围，不再推迟。

## 4. 执行规则

1. 严格按照编号顺序执行，每次只实现并验收一个步骤。
2. 每一步完成后先验证和 Review，再勾选完成并记录到 `REVIEW_LOG.md`。
3. 大厅仍只消费 Manifest 和公共服务，不导入任一正式小游戏脚本或游戏内资源。
4. 两款正式游戏都只通过 `MiniGameContext` 和公共服务请求暂停、退出、反馈、存档与广告，不直接调用 `wx.*`。
5. 正式微信广告实现封装在平台/服务边界内；浏览器预览继续使用可控 Mock。
6. 玩法参数、广告位 ID、广告频控和可调整文案必须配置化，不散落为魔法数。
7. 大厅和每个小游戏分别定义独立视觉规范后再进入制作；不得用公共皮肤抹平差异。所有交互仍必须覆盖正常、加载、空、禁用和失败状态。
8. 修改核心协议、状态机、Bundle、存档结构或广告边界前，先更新架构文档并记录迁移与回滚方式。
9. 未记录设备、网络和测试条件时，不把主观体验写成量化性能结论。
10. 所有外部素材必须具有明确的项目使用许可并进入素材台账；禁止使用来源不明、无法追溯或直接取自其他游戏的资源。
11. 大厅、合成大胖橘与霓虹 2048 分别使用独立声音方向和正式音频文件；不得使用外部平台临时成品替代，也不要求用户另行提供音频素材。

### 4.1 UI 与美术素材来源

- 项目专属视觉：大厅背景、游戏封面、水果、装饰插画和必要的氛围素材，优先使用 ImageGen 按各自视觉单元冻结的规范独立生成，再经过裁切、透明背景、尺寸和压缩处理后导入 Cocos。
- 基础 UI 控件：按钮、卡片底板、面板、进度条、遮罩和分隔元素，优先使用 Cocos 原生节点、`Graphics`、纯色 Sprite 与九宫格制作，避免为简单形状引入大图。
- 通用图标：仅使用许可证明确且允许当前项目用途的开源图标，或按视觉规范自行绘制；不得混用风格冲突的多套图标。
- 中文字体：仅使用授权条款明确、可随项目分发的字体；优先评估 SIL OFL 等许可清晰的字体，并在打包前核对字体文件和许可文本。
- 音效与音乐：由 Codex 在第 23 步通过项目内可复现的程序化合成与编曲脚本原创生成；保留脚本、参数、随机种子、48 kHz WAV 母带、压缩记录和试听结论，并按大厅/游戏独立 Bundle 管理。
- 素材台账至少记录：资源名称、用途、来源类型、原始地址或生成提示词、作者/模型、许可证、生成或下载日期、修改记录、仓库路径和 Bundle 归属。
- 任何素材在来源或许可未确认前只能作为开发占位，不得进入用户试玩候选构建。

  - 验收：不同尺寸水果不穿墙、不明显抖动、不重复合成；一次输入只投放一个水果。

- [x] **第 15 步：完善计分、连锁和里程碑反馈**

  - 验收：每次加分来源可解释；连锁不重复结算；最高级水果不继续越级。

- [x] **第 16 步：完善失败判定与局末冻结**

  - 验收：短暂越线不误判；稳定越线只结束一次；结算期间不再投放或合成计分。

- [x] **第 17 步：设计并实现单局一次续玩规则**
  - 每局失败后最多提供一次激励广告续玩；成功后按冻结规则移除造成危险的部分水果、重置危险计时并恢复游戏。
  - 验收：续玩规则确定、可测试且不会重复领奖；跳过、失败或广告不可用时仍可直接结算或重开。

- [x] **第 18 步：完善存档与历史纪录**

  - 验收：旧版本存档可读取或迁移；中途退出不错误刷新最高纪录；写入只发生在规则规定的时点。

  - 验收：大厅与游戏不复用音乐、音色或正式音效文件；全部声音为项目原创且不依赖外部素材；音乐可无缝循环；开关即时生效；高频碰撞有变体与节流；前后台、广告、暂停、退出和 Bundle 释放不叠加或残留音频；用户试听确认后才能标记为候选可用。

  - 暂停页提供继续、重开和回大厅；失败页提供续玩、再来一局和回大厅；结果展示分数与新纪录。
  - 验收：所有按钮具有默认、按下、禁用和等待状态；快速点击不会重复发起广告、重开或退出。

- [x] **第 25 步：完成 UI 多分辨率与可读性回归**
  - 覆盖短屏、长屏、刘海/挖孔安全区和不同像素密度。
  - 验收：关键按钮可触达，文本不截断，危险线和容器比例不因适配改变玩法公平性。

## 9. E：在广告接入前完成霓虹 2048

- [x] **第 26 步：冻结 2048 玩法、视觉与声音规格**
  - 采用经典 4×4 规则：每次有效移动后生成 2 或 4，同方向一次移动中每块最多合并一次；2048 仅作普通里程碑，首次达成 4096 后进入庆祝层，可继续挑战更高数字、完成本局或返回大厅，无可用移动时结算。
  - 视觉采用深靛黑背景、青绿/琥珀霓虹数字块和克制网格光效；声音采用独立电子脉冲与和弦，不复用猫咪游戏的纸片、猫屋或音频文件。
  - 验收：规则边界、输入、计分、目标、失败、暂停、纪录、动效、声音和适配均有明确口径。

- [x] **第 27 步：建立 2048 独立 Bundle、场景与大厅入口**
  - 新增 `game-2048` Bundle、独立场景和 `MiniGame` 入口，通过 Manifest 在大厅作为第二张标准游戏卡展示。
  - 验收：大厅不导入游戏脚本或游戏内资源；加载、进入、重开、退出和 Bundle 释放继续走公共运行层。

- [x] **第 28 步：实现 2048 规则引擎、计分与可测试模型**
  - 实现四向压缩/合并、随机生成、有效移动判断、2048 普通里程碑、4096 最终目标判断、无步可走判断与分数模型。
  - 验收：左右上下结果确定；无变化移动不生成新数字；同一数字单步不重复合并；有效移动后的棋盘不可回退。

- [x] **第 29 步：完成棋盘 UI、触控/键盘输入与动效**
  - 实现 4×4 棋盘、分数/最高分、暂停、滑动提示、数字块出现/移动/合并反馈和常见竖屏安全区适配。
  - 验收：滑动阈值和主方向判定稳定；键盘与触控结果一致；动画期间输入不产生重复步；短屏/长屏无裁切。

- [x] **第 30 步：接入独立音乐、音效、设置与本地纪录**
  - 原创生成并接入 2048 循环音乐、移动、无效移动、生成、合并、连锁、达成 4096 目标、失败和按钮音效；音乐/音效开关即时生效。
  - 验收：音频位于 `game-2048` Bundle；无缝循环、峰值与生命周期验证通过；最高分和最高数字按独立游戏命名空间持久化。

- [x] **第 31 步：完成暂停、目标、失败、结算、重开和回大厅闭环**
  - 暂停层提供继续、重新开始和回大厅；2048 只提供里程碑反馈；首次达成 4096 提供继续挑战更高数字、完成本局和回大厅；无步可走与主动完成进入结果层。
  - 验收：所有主操作去重；已结束棋盘不会恢复输入；重开产生新 Session；退出释放事件、音频、节点和 Bundle。

- [x] **第 32 步：完成 2048 自动回归与浏览器试玩验收**
  - 覆盖规则样例、输入、目标/失败、暂停、重开、退出、存档损坏、音频开关、短屏/长屏和连续进入退出。
  - 验收：静态检查、资源验证、Creator 预览编译和真实浏览器闭环通过，无新增控制台错误；正式 Web/微信发布包继续在第 41、43 步生成。

## 10. F：接入正式微信广告

- [ ] **第 33 步：定义广告产品规则和频控**
  - 首发只使用激励视频续玩和受控局间插屏；首局不强制插屏，插屏不得在游戏操作中出现。
  - 验收：明确触发点、单局/单日上限、冷却、奖励条件和无广告降级；规则可通过配置调整。

- [ ] **第 34 步：扩展平台无关广告边界**
  - 在现有 `AdService` 基础上定义激励视频、插屏、加载状态、错误和重复调用语义。
  - 验收：业务层不出现 `wx.*`；浏览器 Mock 可稳定模拟完成、跳过、失败、超时和不可用。

- [ ] **第 35 步：实现微信广告 Provider**
  - 封装微信广告实例创建、加载、展示、关闭、错误、销毁和前后台生命周期。
  - 验收：广告位 ID 来自配置；实例不重复创建；监听可解除；SDK 异常被转为公共结果。

- [ ] **第 36 步：接入激励视频续玩**
  - 只有完整观看才执行第 17 步定义的续玩奖励。
  - 验收：完成、跳过、失败、无填充、超时、切后台和连续点击路径均只结算一次；失败不扣除重开或返回能力。

- [ ] **第 37 步：接入受控局间插屏**
  - 仅在自然局末或回大厅的安全时点按频控展示，不在首局和激励广告之后立即叠加。
  - 验收：插屏失败不阻塞导航；关闭后回到正确状态；同一局不会重复展示。

- [ ] **第 38 步：接入广告统计与开发诊断**
  - 记录请求、加载、展示、完成、跳过、失败、奖励发放和频控拦截事件。
  - 验收：事件包含 gameId、sessionId、placement 和结果；不记录广告位密钥或用户敏感信息；同一结果不重复上报。

## 11. G：首个可玩版本验收

- [ ] **第 39 步：执行功能与异常回归**
  - 覆盖两款游戏首次进入直接开局与完整一局，以及猫咪续玩、2048 普通里程碑、4096 庆祝层三个出口/失败、结算、重开、暂停、退出、弱网、前后台、存档损坏和广告全结果矩阵。
  - 验收：任一失败都能恢复到可操作的游戏、结果页或大厅，不需要重启小游戏。

- [ ] **第 40 步：执行生命周期与资源压力测试**
  - 分别连续进入退出两款正式游戏 30 次，并重复执行重开、猫咪续玩广告和大厅返回。
  - 验收：无持续内存增长、重复 Session、监听、音频、粒子、对象池、广告实例或 Bundle 残留。

- [ ] **第 41 步：执行性能、包体和真机基线测试**
  - 在至少低、中、高三个设备档位记录启动、分包加载、帧率、卡顿、CPU/GPU、内存和包体。
  - 验收：记录真实设备与网络条件；低档降级不影响核心玩法；不以未量化的主观判断代替结果。

- [ ] **第 42 步：执行小规模真实用户试玩**
  - 邀请目标用户分别完成两款游戏首次进入和至少两局游戏，记录理解障碍、误触、退出点、广告反感点和再次游玩意愿。
  - 验收：问题按阻塞、高、中、低分级；阻塞首局理解、核心操作或正常退出的问题必须在本阶段修复。

- [ ] **第 43 步：完成候选版本真机回归**
  - 使用修复后的微信构建完成“启动 → 大厅 → 两款游戏 → 各自关键分支/结算 → 重开 → 回大厅”的最终闭环。
  - 验收：正式 UI、玩法、存档、音效、振动和广告均使用候选配置；无开发占位资源与调试入口暴露给普通用户。

- [ ] **第 44 步：关闭第二阶段**
  - 汇总功能、用户试玩、性能、广告、剩余风险和下一阶段输入。
  - 验收：版本达到可交给用户试玩的标准；未完成项明确进入提审发布、数据运营或后续内容计划。

## 12. 本阶段完成条件

- 普通用户从微信冷启动后可以理解统一双列卡片大厅并进入“合成大胖橘”或“霓虹 2048”；列表末尾展示同尺寸且不可交互的“更多游戏，敬请期待”卡，大厅不存在主推游戏样式。

- 首次进入无需引导即可投放；投放、合成、计分、失败、续玩、结算、重开、暂停、退出和存档形成完整闭环。
