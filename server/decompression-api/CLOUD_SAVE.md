# 云存档业务说明

本模块属于 `decompression-api` 游戏后端，接口入口为 `https://api.antcosmos.cn/decompression`。

## 同步规则

- 本设备满足任一条件后永久开启：实际玩法累计 2 小时、单游戏 45 分钟、任一关卡模式通关 20 关、累计在 6 个不同服务器日期登录，或已获得成就。大厅、选关、暂停、后台、广告和结算页面不计玩法时间。旧版已记录的总时长/单游戏时长用于门槛，旧云开发的开启标记和 ACK 不沿用。
- 门槛前只匿名请求一次服务器日期，不登录账号、不读取或上传云存档。每次达标后的冷启动读取全账号存档并与本地合并。新手机也须先在本设备达到门槛，才会读取该账号的云进度。
- 首次开启或迁入新后端立即上传。之后任一事件触发：尚未确认的有效进度提升累计 5 次、新获得成就、非关卡游戏在结算时刷新纪录。新通一关计 1 次；已通关的旧关星数真提升计 1 次，1 星直接到 3 星仍计 1 次；同一次新通关和获得星数不重复计。跨游戏累计，云端导入和重复结算不计。累计场次、累计胜场不当作每局破纪录。
- 普通冷启动不新增上传检查，也没有原来的 48 小时强制保存。之前失败的上传继续重试；开启门槛时仍需完成首次保存。没有变化、没有新时长时跳过空上传。
- 协议内数值逐字段取最大值、星数逐关取最高、成就取并集且保留最早获得日期。游戏内道具、每日领取标记、设置和有效未完成棋盘保留在本设备。尚未接入协议的游戏字段不会凭空同步。耗时/步数等数值越小越好的纪录尚未加入协议，不能直接按最大值新增此类字段。
- 本次冷启动从后端获得 UTC+8 日期后冻结；连续运行跨天、后台恢复均不重新校时。下次冷启动获得新日期后才发新一天的每日赠送。离线未获得可信日期时暂不发放，正常玩法可继续。各设备独立领取。旧版本遗留的未来领取日期在读取可信服务器日时归到当天，当天不补送。
- 请求快照、设备 ID、序号、时长批次先与本地存档一起持久化，再发网络请求。失败按 15 秒到 5 分钟退避，同一批次重试不重新生成序号。确认只扣掉本批的时长和进度计数，期间新产生的记录继续等待上传。迟到的远端进度在大厅安全应用，避免覆盖正在玩的棋盘。

玩法时间使用引擎帧增量，修改手机时间不会增加时长。分析增量从该实现开始实际记录，不能补造更早的历史时长。统计随存档上传，每个账号、设备和游戏分别累计；它只覆盖达到门槛且触发过上传的设备，因此不是全部玩家的实时活跃度。

## 接口与数据库

客户端只使用两个业务接口，登录校验和服务器日期都随本次操作完成：

| 外部路径 | 用途 | 身份要求 |
| --- | --- | --- |
| `POST /decompression/v1/load` | 获取全账号最佳存档，同时返回服务器时间；`clockOnly: true` 时仅返回时间 | 实际读档须 Bearer token 或 `auth: { platform, code }`；仅时间模式匿名 |
| `POST /decompression/v1/save` | 合并进度与本批时长，确认设备序号，同时返回服务器时间 | Bearer token 或 `auth: { platform, code }` |

已开启云存档的玩家每次正常冷启动只发一次获取请求，直接使用读档响应中的时间。未达门槛时也使用获取接口，但只传 `{ "v": 2, "op": "load", "clockOnly": true }`，不登录、不读写玩家数据。累计可信登录日触发开启时，随后才补发真正的读档和首次保存。跨天和后台恢复不重新请求时间。

首次实际读写在请求正文的 `auth` 字段携带宿主平台票据；服务器在同一次请求中验证身份、执行读写，并返回有效期 24 小时的 token。后续请求使用 `Authorization: Bearer <token>`，不重复调用宿主平台登录。401 时在原读写接口内携带新平台票据重试一次，存档批次的设备、序号、进度与时长保持原样；票据只附加到网络副本，不写入本地待重试快照或数据库。所有成功响应都带 `serverTime` 毫秒时间戳与 `serverDay` UTC+8 日期，且禁止缓存。平台 AppSecret、openid、session_key 不发到客户端。

单独的 `/v1/time`、`/v1/login` 已移除。另保留 `GET /decompression/health` 与 `GET /decompression/ready` 供部署和运维检查，游戏客户端不调用；`ready` 检查数据库及登录配置，未配置密钥时返回 503。

## 多平台身份适配

首次获取请求显式声明平台，其余读写和时长协议完全共用：

```json
{ "v": 2, "op": "load", "auth": { "platform": "wechat", "code": "wx.login 返回的临时票据" } }
```

抖音使用 `platform: "douyin"` 和 `tt.login` 的非匿名账号 code。服务端 `login-providers.cjs` 中的适配器使用抖音官方的[小游戏 code2Session 接口](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/develop/server/log-in/code-2-session)，不是小程序的 v2 接口。只返回匿名身份时拒绝建立云存档账号。客户端的 `Platform.getCloudLoginCredential()` 返回 `{ platform, code }`；公共 `CloudSaveClient` 不调用 `wx.*` 或 `tt.*`，也不按运行平台名称猜测身份来源。

服务端从环境配置选择允许的平台和 AppID，再向该平台的固定官方地址验证 code。客户端不能提交或选择 AppSecret、openid、账号主键或验证地址。新增平台在 `login-providers.cjs` 注册 `{ platform, appId, configured, exchangeCode }` 适配器即可；其返回的 `subject` 必须是已经过平台验证的账号标识，不得直接采用客户端自报 ID。存档读写、数据库事务、合并、门槛与去重逻辑不随平台增加分支。

新 token 绑定平台和 AppID；账号按平台、AppID 和已验证账号标识隔离。同平台同 AppID 的同一账号可跨设备同步。微信、抖音账号不能自动判断为同一个人，因此不会自动互通进度；将来需要互通时，应增加验证双方身份的账号绑定流程。

身份数据兼容已部署微信账号：内部验证函数未携带 `platform` 时仅默认微信，错误或未知平台不会回退微信；微信账号继续使用原来的 `SHA-256(AppID + ':' + openid)` 主键，未到期的 v1 微信 token 继续有效。其他平台使用包含平台和 AppID 的独立命名空间。升级不改现有三张数据表，不需要迁移微信存档。

当前客户端只实现微信平台票据获取。后续发布抖音版时，在抖音平台服务中实现 `getCloudLoginCredential()` 和 `requestJson()`，在服务端 `.env` 中配置 `TT_APP_ID`、`TT_APP_SECRET` 并重启，再配置抖音 request 合法域名、完成真机联调。没有配置抖音密钥时不会启用抖音登录，也不会向抖音发送微信凭据。`/ready` 的 `loginPlatforms` 列出当前已配置的平台；抖音适配器目前只完成模拟官方响应的协议验证，不能视为已完成真实抖音接入。

`migrations/0001_cloud_save.sql` 创建三张业务表：`cloud_saves` 每账号一行存最佳进度；`sync_devices` 保存设备最近确认序号和批次摘要；`game_playtime` 按账号、设备、游戏累加实际玩法毫秒数。保存时锁定账号行，将最佳进度、时长累加和序号确认放在一个事务中。重复请求不重复计时，同一序号带不同内容返回 409。

查看游戏累计时长：

```sql
SELECT game_id,
       round(sum(total_ms)::numeric / 3600000, 2) AS hours,
       count(DISTINCT user_id) AS accounts,
       count(*) AS device_records
FROM game_playtime
GROUP BY game_id
ORDER BY sum(total_ms) DESC;
```

协议字段在 `assets/resources/configs/cloud-save.json` 中声明，覆盖当前 17 款游戏；时长游戏 ID 来自 Manifest 清单。客户端与后端共用同一份纯 TypeScript 编解码和合并代码。字段次序、code、星数键与成就 code 是持久化协议，上线后不能复用或随意重排。填色只上传已转换为当前题库格式的存档，避免把旧关号当成新关号；游戏启动时原有本地迁移会完成转换。
