# 微信 CloudBase 云存档

当前状态：客户端、云函数、数据库权限样例和回归测试已接入；尚未创建环境或部署。`assets/resources/configs/app.json` 中的 `cloudSave.enabled` 默认关闭，环境 ID 留空。浏览器预览和其他平台继续使用本地存档。

## 创建环境与部署

1. 在**当前微信小游戏 AppID** 的微信开发者工具中开通云开发，创建环境并记下环境 ID。使用文档型数据库，不需要 COS、独立 SCF 或客户端密钥。环境套餐和费用以开通页面为准，代码不会自动购买资源。
2. 在数据库中新建集合 `cloud_saves`，将该集合的自定义安全规则设置为 `database.rules.json` 的内容：客户端不可读写，只有云函数服务端读写。无需额外索引。
3. 用 Cocos Creator 3.8.8 构建微信小游戏。假设输出目录是 `build/wechatgame`，在项目根运行：

   ```sh
   npm run prepare:cloud-save -- --wechat-project build/wechatgame
   ```

   若构建到了 `wechatgame-001` 等目录，请传入实际路径。该命令生成共用协议的服务端文件，复制到微信工程中的 `cloudfunctions/cloudSave`，设置 `cloudfunctionRoot`，并将云函数目录加入上传忽略项，防止打入游戏包。重新构建覆盖工程配置后需要重新执行。
4. 使用微信开发者工具打开该构建目录，选择刚创建的云开发环境。在 `cloudfunctions/cloudSave` 上右键选择“上传并部署：云端安装依赖”。函数名为 `cloudSave`，入口 `index.main`，运行时选择平台支持的 Node.js 18 或更高版本，超时建议 10 秒。保持微信原生 `wx.cloud.callFunction` 调用方式。
5. 修改 `assets/resources/configs/app.json`：

   ```json
   "cloudSave": {
     "enabled": true,
     "environmentId": "这里填写实际环境 ID",
     "functionName": "cloudSave",
     "requestTimeoutMs": 10000
   }
   ```

   重新构建微信小游戏并执行第 3 步。环境 ID 是公开配置，不是密钥。不同环境之间不自动搬迁存档。
6. 在微信真机上验证：已有 50 关存档首次打开即保存；第二台设备使用同一微信账号、同一 AppID 和环境，清空该设备本地测试数据后冷启动恢复。用测试账号验证，勿删除正式用户的数据。控制台手动执行函数没有微信用户身份，会返回 `UNAUTHENTICATED`；请从小游戏发起真实调用。

官方参考：[微信小游戏原生接入](https://docs.cloudbase.net/quick-start/frameworks/wechat-minigame-native)、[微信云函数](https://docs.cloudbase.net/recipes/add-cloud-function-wechat-miniprogram)、[数据库事务](https://docs.cloudbase.net/database/transaction)、[实例复用与身份上下文](https://docs.cloudbase.net/cloud-function/instance)。入口只读取**本次调用 context** 的微信身份，不从请求正文或复用的进程环境中读取用户身份。

## 已实现的同步规则

- 永久开启条件满足任意一项：某关卡模式通关 50 关、单游戏实际游玩 2 小时、任意累计 5 个自然日每天游玩 30 分钟、全部游戏累计游玩 4 小时。大厅、选关、暂停、后台、广告和结算界面不计时。新版本首次启动立即评估旧进度；旧版本没有记录的游玩时长无法补算。
- 触发：首次开启、各游戏累计新增未保存通关 25 关、新获得成就、冷启动距离上次上传超过 48 小时。重玩旧关不增加通关计数。没有待上传数据就跳过；48 小时检查不会在前台循环触发。
- 上传只发送关键字段发生变化的游戏模块，以及发生变化的已获得成就模块。一次请求批量处理，未发送的模块不动。存档数据使用变长整数和 Base64，星数每关 2 bit，尾部空星数省略；成就代码和日历日期用整数编码。
- 游戏模块按进度选**完整模块**：高进度全部替换，低进度忽略，进度相等时最后一次成功保存的完整模块替换。不会逐关合并星数，也不会挑选各字段最大值。无关卡游戏按最高分比较；有普通/困难模式的游戏按两种模式的已通关数之和比较。
- 成就模块只存已获得的成就，跨设备做并集，相同成就保留最早获得日期。未获得成就的进度由获胜的游戏模块中的玩法指标恢复。日期按玩家当时的日历日期保存，恢复保留原日期，不补造具体获得时分秒，不重复播放领奖动画。
- 本地无游戏/成就存档时冷启动尝试恢复。网络失败会保持“待恢复”，与“云端明确无存档”区分；迟到响应在启动/大厅应用。等待期间离线产生的本地进度参与完整模块比较，本地更高或相同进度保留，云端更高则整份替换。已存在本地存档时不主动拉取云端覆盖它。
- 请求快照和序号先写入本地，再发网络请求。成功后只确认所发送快照，期间产生的新进度保持待保存；失败以 15 秒到 5 分钟退避重试，回到前台可再尝试。服务端按设备序号去重，旧请求重试不会覆盖另一台设备后来写入的同进度模块。

## 存储与维护

每个玩家一个文档，`_id` 是 AppID 与 OPENID 的 SHA-256。`m` 是按游戏代码分开的压缩模块，`a` 是已获得成就及日期，`c` 是每个安装实例最近确认的请求序号，`updatedAt` 是服务端时间。事务一次读取并原子写回该玩家的小文档，以保证并发设备不会丢掉彼此的模块。这里的“模块”是逻辑模块，不需要为每个小游戏建立集合。

最多保留 128 个安装实例的序号。达到上限后拒绝新增实例的保存，不会通过淘汰回执破坏去重；出现 `DEVICE_LIMIT` 时需检查该测试账号是否反复重装或清空数据。客户端上报的游戏进度不是防作弊证明，本功能只处理存档和一致性。

关键字段在 `assets/resources/configs/cloud-save.json` 声明，公共服务不导入游戏 Bundle。已接入全部 10 个游戏。小游戏的游戏内道具、设置、未完成棋盘、自选图片、游玩次数等不进云存档。画线救狗只读写当前版本的关卡编号和星数，开发期间的其他版本不迁移、不上传。泡泡龙恢复星数但不伪造最佳发射次数记录。

代码、字段顺序、关卡编号映射和成就代码属于持久化协议。上线后不能重用、调整既有编码来表达其他含义；协议变更需增加新版本和迁移逻辑，并保持已部署客户端兼容。修改编码或清单后运行：

```sh
npm run prepare:cloud-save
npm run verify:cloud-save
```

云函数 `generated` 目录由客户端的纯 TypeScript 协议源码生成，不手工修改；测试会检查文件是否过期。环境未创建时本地验证使用有冲突重试的数据库替身，不会连接或产生线上云开发费用；真实身份透传、数据库权限与设备网络仍须部署后真机联调。
